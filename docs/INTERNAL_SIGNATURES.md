# Adding internal signatures

The internal C++ extraction recovers functions without symbols from `.eh_frame`
and from RTTI vtables. Two optional parts of `app/src/main/assets/patterns.json`
let you attach a human name to a function the binary cannot name by itself.

Both lists are additive. A pattern that matches nothing is reported as
`not_found`; a pattern that matches more than once is reported as `ambiguous`
with every candidate listed. The extractor never guesses.

## Internal byte signatures

```json
{
  "internalPatterns": [
    { "name": "Level::tick", "pattern": "FF 03 01 D1 ?? ?? 02 A9", "resolve": "self", "offset": 0 }
  ]
}
```

- `pattern` is a sequence of hex bytes. `??` matches any byte.
- `resolve` controls which address is reported:
  - `self` reports the match address plus `offset` (default).
  - `bl_target` decodes the first `BL` inside the match and reports its callee.
  - `adrp_add` decodes an `ADRP`+`ADD` pair and reports the global it points at.
  - `prologue_back` walks back to the nearest verified function start from the
    `.eh_frame` table.
- `offset` is a signed byte adjustment applied by `self`.

Keep the pattern short and specific. A four-instruction window that includes a
call or a global reference is usually unique; a bare prologue is not.

## String anchors

```json
{
  "stringAnchors": [
    { "name": "Actor::setName", "string": "actor_name" }
  ]
}
```

The extractor finds the string in `.rodata`, then finds every `ADRP`+`ADD` or
`ADRP`+`LDR` pair in `.text` that materialises its address. Each reference is
mapped to its enclosing function through the `.eh_frame` table.

Prefer a string that appears once. A common log prefix will produce dozens of
candidates and an `ambiguous` result.

## How signatures are made unique

Every function the extractor can name gets a signature: the shortest prefix of
its normalised instruction stream that no other function start shares.

Normalisation wildcards what a rebuild changes and keeps what identifies the
code:

| instruction | kept | wildcarded |
|---|---|---|
| `ADRP`, `ADR` | opcode, `Rd` | `immlo`, `immhi` |
| `B`, `BL` | opcode | `imm26` |
| `B.cond`, `CBZ`, `CBNZ`, `TBZ`, `TBNZ` | opcode, `Rt`, condition | branch displacement |
| `LDR`/`STR` (unsigned offset) | opcode, `Rn`, `Rt` | `imm12` |
| `LDR` (literal) | opcode, `Rt` | `imm19` |
| `MOVZ`, `MOVK`, `MOVN` | opcode, `Rd`, `hw`, `sf` | `imm16` |
| `ADD`/`SUB` immediate | opcode, `Rd`, `Rn`, `sh` | `imm12` |
| everything else | every bit | nothing |

The signature is a word stream plus an AND mask, so a partially masked
instruction (a `MOVZ` keeps its shift, an `ADR` keeps its register) stays
distinguishable instead of collapsing to a whole-byte wildcard.

The engine makes **one** pass over `.text`:

1. collect the first eight normalised words at every function start;
2. sort by those words and measure the longest common prefix of each neighbour;
3. a function whose prefix no neighbour shares is unique at that length;
4. functions that share their *whole* body are one group: they cannot be told
   apart by bytes at all, so they are grouped (`identicalGroup`,
   `identicalGroupSize`) and each member gets an `anchor` locator instead.

Nothing is re-scanned per round, so the cost is a sort plus a linear sweep no
matter how many functions share a prologue. The stage reports `textPasses: 1`
and `Signatures: 1 text passes, …` in the live log.

Anchors, in order of preference: a `Class::vfunc_N` slot that calls the
function, a single distinct caller, a single data reference, the first call
site, and finally the member's ordinal inside its identical group
(`group:<id>/<size>#<ordinal>`: resolve the shared pattern, take the Nth hit).

## Measured on the host

`src/bin/bench.rs` runs the same stages as the JNI entry point and prints wall
time plus `/proc/self/status` resident memory per pass:

```bash
cargo run --release --bin bench -- /tmp/scale_a.so
```

The fixture is generated by `scripts/scale_fixture.py`: a synthetic but
structurally real AArch64 library with `.eh_frame` FDEs, RTTI type_info objects,
vtables, symbols, strings and thunk families. 800,000 functions, 48.7 MB of
`.text`, 6,386 vtable groups, 480,000 named functions.

| stage | this engine | the round-based engine it replaced |
|---|---|---|
| `.eh_frame` | 27 ms | 26 ms |
| cross-references and naming | 330 ms | 337 ms |
| **signature planning** | **294-316 ms** | round 1: 1.4 s, round 2: **846 s, unfinished** |
| writing the table | 7.7 s | never reached |
| whole pipeline | **9.2-9.3 s** | killed at 900 s |
| peak resident | **619-635 MB** | 565 MB and climbing at round 2 |

The old engine's log for the same file:

```text
  2417 ms ... 80% Signatures: 0 resolved by prefix, 466757 need scanning
  2422 ms ... 80% Signatures: round 1 (48 bytes, 466757 candidates)
848667 ms ... 82% Signatures: round 2 (64 bytes, 420591 candidates)
```

That is the owner's "took minutes and then ran out of memory at round 19": each
round re-rendered every pattern as hex text, rebuilt the matcher and swept the
whole of `.text`, and the pattern set only shrank by a few percent per round.

Result on the fixture: 496,600 signatures, **417,721 unique** (84.1 %), 78,879
grouped with an anchor. The remaining gap is exactly the thunk families: 400
byte-identical members per family cannot be separated by any byte pattern.

The planner runs on one thread on purpose. Sorting the heads and measuring their
common prefixes is a linear sweep over a few megabytes, so the parallel version
measured 234 ms against 298 ms serial: seventy milliseconds is not worth a
worker pool, its per-thread buffers and its start-up on a two-gigabyte phone.
The only remaining pool is the Part 1 pattern scan, and it is capped at two
threads below three gigabytes of RAM (`src/limits.rs`), four above.

`signatureStability` is the share of signature bits that are literal, so a mod
can rank locators by how likely they are to survive a rebuild (57 % for the
average function above, 100 % for a body with no branch or global reference).

## Testing a new entry

```bash
cd app/src/main/rust/offset_core
cargo test
```

Then run a scan and check the live log for
`[RUST] Pass D/E: X verified, Y ambiguous, Z not found`. A `not_found` entry is
harmless; it is reported so a stale signature is visible rather than silent.
