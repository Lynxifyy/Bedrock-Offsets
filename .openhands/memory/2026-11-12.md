## Flag 2 — the pack (the real defect)
The pack held 10 **instruction-shape** patterns (`frame_push_x29_x30`,
`pacibsp_prologue`). Each matched thousands of places and was named after
nothing, so `verify_against_symbols` found no symbol with that name → every hit
`UNVERIFIED` → **confidence permanently 0**. Measured: 12,374 raw matches,
8,191 discarded as non-prologues, 0 verified.

Fix, in two parts:
1. **New `scripts/derive_patterns.py`** — parses `.dynsym`, keeps defined
   `Java_*` symbols, and grows each signature from the symbol's bytes until it
   is unique in `.text` (8..64 bytes, step 4). 91 unique signatures.
   - **Gotcha that cost a debug cycle**: the in-`.text` index is
     `st_value - text.sh_addr`, NOT `st_value - delta` (`delta = sh_addr -
     sh_offset` is the *file-offset → VA* direction). Using `delta` put every
     signature `0x6834c80` bytes (= `.text`'s address) into the section.
   - `bytes.count` **skips overlaps**; uniqueness needs a `find` loop or a run
     of identical bytes looks unique at the first length.
2. **Pipeline order fix** (`jni_bridge.rs` + `scanner/verifier.rs`) — the
   prologue check ran **before** the symbol cross-check, so it discarded
   correct offsets whose shape is not a stack frame. A **leaf** is exactly that
   (`isEduMode` = `mov w0, wzr; ret`): 27 of 91 confirmed offsets were lost.
   Now the cross-check runs first, and `verify_prologues` keeps a hit whose
   `verification_status == Verified` even when `verdict.accepted` is false
   (and leaves `prologue_kind = None` so the row's detail is not a lie).

Result on the real library: **91/91 matched, 0 discarded, 91 verified,
0 conflicts, 100% confidence.**

## v1.0.5 — the RTTI crash (device, after a successful scan)

**Symptom.** On a real device the app got all the way through SAF → streaming
extraction (hash `2abbb29…`, 342,231,392 bytes) → zero-copy mmap → AArch64 →
entry point `0x0`, 28 sections, and then the log stopped. No error: the process
was killed.

**Root cause.** `rtti.rs` read the library's whole `.rela.dyn` into a flat
`Vec<Relocation>` — 1,043,633 entries × 24 bytes — and then copied the supported
ones into a second vector before dropping the first. About 64 MiB of transient
heap, on top of the scan's resident set, inside the process heap cap. The kernel
kills the app instead of letting the engine return an error, so nothing gets
logged.

**Fix (three parts, all in `rtti.rs`).**
1. `RelocationIndex::build` streams `.rela.dyn` in bounded `BLOCK_ENTRIES` blocks
   and filters as it reads (`is_supported_relocation`), so only the sorted index
   is allocated. Uses `try_reserve` → `CoreError::OutOfMemory`.
2. `collect_vtables` resolves each candidate's class name in the same pass and
   keeps only resolved vtables, so the 227,513-candidate vector is gone. Sort
   order is by `type_info_address`, so the first-wins rule stays deterministic.
3. The dead relocation pages are released (`PageReleaser`) after indexing and
   before `.data.rel.ro` is faulted in, so the two phases' resident sets stop
   stacking. `resolve_vtables_with_releaser(image, Option<&dyn PageReleaser>)`;
   `resolve_vtables_json` passes the `MappedLibrary` as its own releaser.

**Measured** (real 342 MB lib): phase heap 64 → <40 MiB; pipeline peak RSS
86.4 → 53.7 MiB; scan peak 21.2 MiB. Output identical: 4,688 vtables, 1,098,640
relocations. Budget test `rtti_memory_test.rs` failed at 64 MiB before the fix.

**Gotcha for next time.** `.rela.dyn` in this lib is *not* sorted by offset
(13,418 out-of-order entries), so the index cannot be replaced by a streaming
merge — the sort is load-bearing.

**Device-only number left open.** The device reported 165.3 MB during the *scan*
phase where the host measures 21.2 MiB. Not reproduced. Suspects: the two
concurrent `ProgressCallback` objects, and the JNI string marshalling of the
payload.

## Bedrock-Offsets review-findings PR (branch `fix/review-findings`, PR #11)
16 findings fixed, one commit each. Recurring lessons worth keeping:
- **`onTrimMemory` is not the only pressure callback**: also override
  `onLowMemory()` (deprecated but still delivered) and route it to the same
  `onMemoryPressure()`. Guarded by a Robolectric `MainActivityTest` case.
- **Compose `ModifierParameter` lint**: `modifier` must be the FIRST optional
  parameter. Adding a defaulted param (`lastBuildId = ""`, `fillHeight = false`)
  *before* `modifier` fails `:app:lintDebug` (CI runs it). Move it after.
- **Cancelling a Kotlin coroutine does NOT stop a blocking JNI call.** `scanText`
  is synchronous in native, so `job.cancel()` left the Rayon workers running.
  Fix: Rust `scanner::begin_scan()` registers the in-flight scan in a
  `OnceLock<Mutex<Option<(generation, Arc<ScanControl>)>>>`; `ScanGuard`'s `Drop`
  clears the slot only if it still owns the generation (so a late drop can't
  unregister a newer scan). New JNI export
  `Java_..._NativeLib_cancelScanNative` → `cancel_active_scan()`;
  `NativeLib.cancelScan()` is a no-op when the .so is absent. `cancel()`/
  `cancelBatch()` call `engine.cancelScan()` before `job?.cancel()`.
- **CI rustfmt can differ from the container's** on long method chains: CI broke
  `names\n    .contains(&"long_string")` into `names.contains(\n &"long_string"\n)`
  while local `rustfmt 1.10.0` accepted both. When the Rust job fails only on
  `Check formatting`, fetch the job log (`/actions/jobs/{id}/logs`) and copy the
  exact `Diff in ...` form.
- **`GSON_MODEL_CLASSES` count is now 30** (was 31): deleting the unused
  `ProgressTracker` model required removing its entry in `scripts/verify_release.py`.
